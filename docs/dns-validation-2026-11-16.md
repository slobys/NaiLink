# 0.6.86 DNS 修复与实机验证

设备：NanoPi R4S，ARM64 iStoreOS 25.12.6，Linux 6.12.112。测试使用原有节点、DNS 和分流配置，Windows 系统代理关闭，PassWall 停止。

## 修复内容

dae 已有处理 TCP DNS 的代码，但内核健康门控仅为 UDP/53 放行。TCP 查询被送往没有节点健康探测结果的控制面虚拟出口，在握手阶段被丢弃。修复让 TCP/53 同样进入 DNS 控制面；显式阻断判断仍在门控之前，上游、分流及非 DNS 流量不变。

sing-box / TPROXY 的 IPv6 DNS 请求在具有多个 LAN IPv6 地址时，UDP 回复可能使用不同于 REDIRECT 目的地的本机地址，不能匹配反向 NAT，导致内部端口直接出现在客户端回包中。修复增加标准 DNS 传输入口，通过包信息保留实际 IPv6 目的地址；客户端看到的回复仍来自原始 DNS 地址与 53 端口。入口将请求按原 TCP / UDP 方式转给回环上的 sing-box DNS，不另选上游、不更改拒绝结果，也不增加远程健康探测。

监听入口受 NaiLink 自有防火墙守卫保护，仅在 TPROXY 模式启用。停止和启动失败时关闭入口，随后释放自身网络资源。现有内核版本继续使用，不需要替换成未经审核的上游版本。

开发程序在正式 0.6.85 安装上临时运行，原程序与完整配置已备份。它重新编译了修改后的 eBPF 对象，未复用旧对象；SHA-256 为 `bb0f9f0a02e06087019409779e6509f1d81dba38d4337ef7d5c2960ce6705e71`。

每种方式重复十轮四项 DNS 查询和一项 IPv6 UDP 回包身份检查，共 250/250 通过。UDP 客户端连接到指定地址和端口，错误来源会被真实套接字丢弃；另用未连接套接字核对回包来源，避免仅看到 DNS 答案就误判成功。三个内核另在浏览器执行 IPv6 检测，dae / sing-box TUN / mihomo TUN 均为 10/10。

首次切换 sing-box 曾因节点域名解析失败触发自动回退，之后同一程序重新启动成功；两个公网探针各有一次超时。失败记录单独保留，后续五种方式的完整重复检查和 40 个联网探针均通过。没有删掉失败日志或降低就绪条件。

本次保留 124 个节点、3 个订阅、3 个群组及绑定，配置、DNS、路由、订阅链接和计划、账号与 UCI 用户字段一致；订阅刷新时间允许后台自然更新。测试后恢复原来的 dae / TUN 存储选择。

## 回归与边界

- 自动化网络命名空间加入多个 LAN IPv6 前缀，以连接型 UDP 套接字验证回复来源，并增加 IPv4 / IPv6 TCP DNS，覆盖原来的两项故障。
- DNS 入口单元测试覆盖 TCP / UDP、IPv4 / IPv6、上游拒绝、UDP 截断后 TCP 查询、停止与端口释放。复用已有 DNS 库，没有新增大型依赖。
- 现有 `ipversion(6) -> direct` 路由继续保留。普通 Google 强制 IPv6 直连失败的使用限制不属于此次 DNS 修复，不以改写用户路由消除该差异。
- 公网 IPv6 VPS 尚未提供，仍不宣称已完成真实公网 IPv6 节点的全部协议验收。测试边界与 [0.6.85 记录](ipv6-validation-2026-11-16.md) 分开保存。

开发程序结果与最终 CI 正式安装包的摘要、安装验证分别记录；后者须在正式发布前完成。
